Nous devons refactorer complètement l’architecture financière de l’application pour adopter un modèle comptable basé sur un ledger (double entrée).

Objectif :

financial_accounts devient le wallet universel

ledger_entries devient la source de vérité des soldes

user_wallets devient uniquement une couche de sécurité / KYC

wallet_transactions reste l’historique visible utilisateur

Supprimer toute dépendance au champ balance comme source de vérité

🧱 ÉTAPE 1 — Corriger la structure des relations

financial_accounts devient l’unique entité représentant un wallet.

Un wallet peut appartenir à :

un user (ownerUserId)

une shop (ownerShopId)

un tournoi (via metadata si nécessaire)

la plateforme

Le champ type détermine la nature du wallet :
USER_WALLET
SHOP_WALLET
TOURNAMENT_POOL
PLATFORM_ESCROW
PLATFORM_FEES
SYSTEM_ADJUSTMENT

ledger_entries

Chaque mouvement financier doit créer AU MOINS deux entrées :

un débit

un crédit

Le solde réel d’un wallet = SUM(credit - debit)

user_wallets

Devient une extension de sécurité liée à un wallet financier

Ajouter financialAccountId

Supprimer balance ou le garder uniquement comme cache

Contient uniquement :

pinHash

KYC

failedAttempts

verrouillage

wallet_transactions

Doit référencer financialAccountId

Ne doit pas être utilisé pour calculer les soldes

Sert uniquement d’historique utilisateur

Supprimer toute logique métier qui modifie directement un champ balance.

🧮 ÉTAPE 2 — Corriger les filtres et requêtes

Toute récupération de solde doit utiliser :

SUM(credit - debit)
FROM ledger_entries
WHERE account_id = ?

Les requêtes de transactions utilisateur doivent :

passer par son financial account

filtrer proprement par ownerUserId

Vérifier toutes les jointures :

éviter les dépendances directes sur user_wallets.balance

utiliser financial_accounts comme pivot principal

⚙️ ÉTAPE 3 — Corriger les Server Actions & API

Créer une fonction transaction atomique :

executeTransaction({
fromAccountId,
toAccountId,
amount,
type,
metadata
})

Cette fonction doit :

Ouvrir une transaction DB

Vérifier que le solde est suffisant (via ledger sum)

Créer :

une ledger entry débit

une ledger entry crédit

Créer un wallet_transaction pour affichage

Commit

Rollback si erreur

Aucune autre action serveur ne doit modifier les soldes directement.

🖥️ ÉTAPE 4 — Corriger composants & pages

Toutes les pages affichant un solde doivent :

appeler une fonction getWalletBalance(accountId)

ne jamais lire un champ balance directement

Les dashboards shop/tournoi doivent :

récupérer leur financial_account

calculer les soldes via ledger

Supprimer toute logique front qui dépend d’un champ balance stocké.

🛡️ RÈGLES IMPORTANTES

Le ledger est la seule source de vérité.

Aucun update direct de balance.

Toute opération financière passe par une transaction atomique.

Les comptes financiers sont indépendants des users.

Les shops et tournois ont leurs propres wallets.

Objectif final :
Obtenir une architecture financière scalable, cohérente et prête pour des paiements réels.
